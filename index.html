Gym Management

A gym managed end to end: members book classes, trainers run them, and admins watch the numbers.

Group project · Linguagens e Tecnologias Web · 2026

Gym Management is a full-stack web app built as a group project for Linguagens e Tecnologias Web, in PHP with a SQLite database and JavaScript on the front end.

Every user can register, log in and out, and edit their profile, including name, username, password and photo. From there the app splits by role.

Three roles, one database.

Members browse the class schedule and filter it by type, trainer, day or time, then enrol in or cancel upcoming classes, subject to each class’s capacity. They can also read trainer profiles, check which equipment is free in the main training area, and rate and review the classes they have attended.

Trainers manage a public profile with their bio, specialisations and certifications, see who is enrolled in their classes, and keep track of their own schedule. Admins manage members and trainers, the class catalogue and its trainers, and the equipment in the main training area, and can promote any user to admin.

The schedule page uses AJAX live search, so the list of sessions updates as a filter changes, without reloading the page. Trainers and admins also get analytics dashboards: attendance, ratings and engagement for trainers, and popular classes, equipment usage and member retention for admins.

Before writing any code we drew the interface in Figma and sketched a UML domain model. We then built the app in stages, starting with sign-up, profiles and the class list.

Scheduler

A study planner that finds the time for you and warns you when your plans collide.

Group project · Engenharia de Software · 2026

Scheduler is a mobile app for students, written in Flutter for Engenharia de Software. A team of five built it over four Scrum sprints, with the work tracked in GitHub Projects.

It grew out of a familiar problem: always running late and leaving projects to the last minute. Scheduler lets you choose the hours you want to give to studying, the gym or time out with friends, and then organises your week around them.

Five people, four sprints.

Students add their class timetable and set their preferred study days, times and subject priorities. The app allocates study sessions around what is already booked, and does not let you create an event that overlaps another. Sessions can also be planned with friends, once you have found them in the app and can see when they are free.

The plan also includes some gamification to keep people going through the semester: finished sessions earn XP, build a streak of consecutive days and unlock achievements.

We designed it as a client and a server: a Flutter app for the interface and local caching, with a REST API behind it for the scheduling rules. Inside the app the code is split into presentation, business logic and data layers, using patterns such as repositories and view models to keep the screens simple.

Every push or pull request to the main branch ran through GitHub Actions, which set up Flutter, installed the dependencies, linted the code and built the app. We wrote user stories before building and tracked each sprint on the project board.

Pirates Duel

Two players, one cannon each, and a graphics pipeline written from scratch on MINIX.

Group project · Laboratório de Computadores · 2026

Pirates Duel is a turn-based game for two players, written in C as a group project for Laboratório de Computadores and running on MINIX. We built nearly everything from scratch.

The idea is Worms-style turns with Angry Birds-style aiming. Two players share a keyboard and mouse and take turns controlling their pirate ships. The goal is to sink the other ship with cannonballs, and the loser must walk the plank.

Drivers first, game second.

Aiming works like a slingshot: you click and drag with the mouse, and the distance between the cannon and the cursor sets the speed and direction of the shot. A line drawn with Bresenham’s algorithm shows the pull, gravity bends the shot into a parabola, and a hitbox overlap test (AABB) decides whether it lands. We only run that test while a projectile is in flight, to protect the frame rate.

The world is wider than the screen, so a camera follows the cannonball from one ship to the other, easing towards it with linear interpolation. To avoid flicker, each frame is drawn into a back buffer and copied to video memory in one go. Text uses a pixel font stored as bit masks, instead of a sprite for every letter.

The game runs in VBE mode 0x14C, at 1152×864 in 32-bit colour. The timer ticks at 60 Hz and drives gravity, the camera and the 15-second turn limit. The keyboard starts, pauses and quits the game, and the RTC feeds an on-screen clock that is read only once a second so it never causes lag.

The code is split into controllers for the hardware drivers, a model for the shared data, logic for the rules and physics, and a view for rendering. A redraw flag means the screen is only updated when something has actually changed.
